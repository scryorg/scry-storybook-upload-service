# Dashboard import: upload service contract (PR 1)

The dashboard (feature `dashboard-import`) imports a folder of design files in the browser, zips them into an SCF
bundle, and uploads it through the upload service. This is the service half of that contract. The fixtures under
`test-fixtures/dashboard-import/` are generated by `src/app.dashboard-door.test.ts` from this service's real responses;
the dashboard's mock service and contract tests read them, so the two repos cannot drift. Regenerate with
`npx vitest run src/app.dashboard-door.test.ts`.

## The second door

Header `X-Scry-Caller: <HS256 JWT>`, valid on exactly two routes (POST only):

| Route | Purpose |
|---|---|
| `POST /presigned-url/:project/:version/bundle.zip?source=x-adobe-bridge:<platform>` | create a `bundlePending` build, return a presigned PUT url |
| `POST /upload/:project/:version/bundle/complete` | validate the uploaded zip and queue processing |

Signed with `SCRY_UPLOAD_ASSERTION_SECRET`, shared with the dashboard. Claims (all required):

| Claim | Rule |
|---|---|
| `sub` | the Firebase uid; becomes the build's `uploadedByUid`; never logged (a 12-hex salted hash is) |
| `aud` | exactly the string `scry-upload` |
| `prj`, `ver` | must equal the route's `:project` and `:version` |
| `src` | `x-adobe-bridge:<platform>`; on presign it must equal `?source=`; on complete it must equal the build's stored source |
| `iat`, `exp` | integers; `exp - iat` in 1..60 s; 5 s skew allowed on both sides |
| `jti` | 8..128 chars of `[A-Za-z0-9_.:-]` |

Header must be `{"alg":"HS256"}`; `none`, HS384/512 and anything else are refused. The signature is verified (constant time)
before any claim is read. See `test-fixtures/dashboard-import/assertion.json` for a signed example with a test secret.

### Decisions

- **Fail closed.** Secret unset: the header is ignored and the routes behave as API-key only (the same 401 as no credentials).
  This is also the off switch.
- **Both headers.** If `X-Scry-Caller` is present (secret set, eligible route) the assertion alone decides: a valid one wins,
  a bad one is a 401 and never falls through to `X-API-Key`. Without `X-Scry-Caller` the API key path is unchanged.
- **Replay.** A replayed assertion inside its lifetime (at most 60 s) is accepted; there is no `jti` store. A replayed presign
  creates another pending build the orphan sweeper removes; a replayed complete re-validates the same object. Tested and intentional.
- **Single refusal body.** Every assertion failure is `401 {"error":"unauthorized","request_id":"..."}`. (`request_id` is added by
  the service's existing request-id middleware to every error body.) The reason is only in the log.
- **Build ownership.** A dashboard-door build records `channel: "dashboard"` and `uploadedByUid`. Complete through the door
  only works on a build with channel `dashboard`, the same uid, and the same `src`; anything else is `404 {"error":"Build not found"}`
  (identical to an unknown build). The door cannot complete an API-key build and the API-key path is unchanged.
- **Request ids.** After the assertion verifies, the dashboard's `x-scry-request-id` is adopted, echoed in the response header,
  and forwarded to the processing queue. Before verification it is ignored.

## Exchange

1. `POST presign` -> `200 {url, fields:{key}, buildId, buildNumber}` (`start.*.json`). The browser PUTs the zip to `url`
   (needs R2 CORS, see `dashboard-import-cors.md`).
2. `POST complete {buildId, zipKey, skippedExtCounts?}` -> `200 {success:true, queued:true, buildId, buildNumber}` (`complete.*.json`),
   or `422 {success:false, errors:[{code,message}]}` with the object deleted and the build marked `failed` (`error.422.json`),
   or `404` (`error.404.json`), or `400` if the object was never uploaded (the build stays pending).
3. A pending build is never reported completed: `processingStatus` is only written by complete (queued) or a failed cleanup.

### `skippedExtCounts` (optional, complete body)

Counts of file extensions the browser skipped, e.g. `{"psd":3,"tiff":1}`. Keys must match `[a-z0-9]{1,5}`, at most 20 keys,
values positive integers capped at 100000. Anything else (wrong type, bad keys) is silently ignored, never a 4xx.
It is only logged.

## Log codes (schema v1; the channel and counts ride in `err_code` because the shared schema has no such fields yet)

| Level | msg | err_code | Extra fields |
|---|---|---|---|
| info | `import start` | `import_start` | `request_id`, `project`, `build_id`, `uid_hash` |
| info | `import complete` | `import_complete` | same |
| info | `import skipped` | `import_skip_<ext>_<count>` (one line per extension) | same |
| warn | `import denied` | `import_denied_<reason>` | `request_id` only (nothing request-controlled) |

`<reason>` is one of: malformed, alg, signature, claims, aud, expired, early, lifetime, project, version, source, subject;
`import_denied_build` means a verified caller tried to complete a build it does not own.
No log line or error body ever contains the token, the secret or the uid.
